## Exact production scope

- `lib/core/media/media_models.dart`: strict six-field reference and nine-field
  status DTOs; enum/MIME/UUID/UTC timestamp/integer validation. Extra fields
  (including URLs), missing fields, coerced numbers and invalid READY fail closed.
  Pre-inspection nullable metadata remains nullable, never fabricated as READY.
- `lib/core/media/media_identity.dart`: captures existing user ID + identity
  generation and subscribes to the supplied Listenable. Same-identity token
  rotation is allowed; logout/account ABA permanently invalidates the scope.
  Pending I/O is raced against cancellation; even already-started late errors are
  observed and discarded after identity loss.
- `lib/core/media/media_api_transport.dart`: dedicated fixed-route metadata,
  raw PUT and controlled binary GET operations. This file is a Dart `part` of
  ApiClient, so it shares its private HTTP client, token provider and existing
  refresh singleflight without exposing tokens through another interface.
- `lib/core/media/media_files.dart`: bounded stream capture into a newly created
  app-owned temporary directory, and controlled download to a temporary file.
  Files are not returned until exact byte/MIME checks finish. Failure/cancellation
  removes partial files; logout also removes completed cached files. The original
  selected input file and the caller's parent directory are never deleted.
- `lib/core/media/media_upload_coordinator.dart`: one scope/file/allocation key,
  singleflight, original server ID, monotonic version/state, read-only recovery.
  Reconstructing with the same scope/key/source/API returns the same coordinator;
  changing the source under the old key or the key for the same source is rejected.
- `lib/core/network/api_client.dart`: **only four added lines** (two imports and
  the part declaration with spacing). Existing JSON methods, 2MB response limit,
  token/session models and refresh implementation are unchanged.

No AppDependencies, route catalog, plugins/pubspec, pages, mic/manager/gift,
Backend, deployment or vendor files changed. No automatic runner is introduced.

## Limits and transfer behavior

Exact decimal limits: image 10,000,000 bytes; voice 10,000,000 bytes and
60,000ms; video 100,000,000 bytes and 30,000ms. Counts are dynamic9, support3
**per create or reply**, private1, with duplicate IDs rejected and selection
order unmodified. Images have duration0; timed media require positive duration.
Local duration is a preflight check, not server inspection evidence. Actual
capture/upload/download chunk lengths are counted, including short/oversized
streams; metadata never makes an over-limit stream acceptable.

All destinations come from configured Backend + internally constructed UUID
paths. No server-returned upload/download URL is consumed. Redirect following is
disabled for every new media operation, including metadata, so no Location hop
can receive the Bearer. PUT is `application/octet-stream`, with no Content-Encoding.
Controlled GET accepts the reference's exact detected Content-Type, no encoded
response, and exact reference bytes (including when Content-Length is absent).
JSON metadata/error bodies retain the existing 2MB bound; binary uses bounded
chunks into a temporary file, not a 100MB JSON/String/BytesBuilder.

Token is captured before `openUrl`; current tuple is checked before send, after
awaits, for every chunk and before/after refresh. Media and ordinary identity-bound
JSON requests share the existing refresh flight. Safe reads and fixed JSON
commands may retry once under the same identity. **PUT never retries after 401**,
even if refresh succeeds; return the error and query the original asset.

## Recovery and future host integration

| Last evidence | Explicit next action |
| --- | --- |
| Allocation response lost, no known ID | `advance()` repeats original allocate key + purpose only; no client-generated asset ID. |
| Known ID, any uncertain upload/complete | `recover()` issues GET that ID, with no new PUT/scan/allocation. |
| ALLOCATED, no prior PUT attempt | `advance()` can perform the first PUT. The attempt marker is set before opening the connection. |
| ALLOCATED after an uncertain PUT attempt | No second PUT; retain the original identity and require explicit user handling/reselection. |
| UPLOADING / QUARANTINED | After current GET, explicit `advance()` may complete using that exact state version. 40983/50381 preserve original metadata/key; no fabricated terminal state. |
| READY | Return strictly parsed reference; repeated advance performs only GET. Binding still belongs to the future domain repository. |
| REJECTED / REVOKED / expired | Surface status, no automatic new asset/PUT/complete. |

`recover()` joins an already active flight rather than starting a parallel read;
it does not itself introduce writes. Concurrent advance calls use the same future.
Regressing versions/states, changing ID/purpose/expiry, or response byte counts
that disagree with the immutable selected copy are rejected before replacing
current metadata. Client-reported duration is not required to equal server probe
duration; both must independently fit the frozen limits.

Future App integration must create a scope from `sessionManager.session?.userId`,
`identityGeneration` and its Listenable, without adding token storage. Retain the
scope, upload copy and coordinator above page lifetimes; do not dispose an unknown
upload merely because a sheet closes. Scope loss discards all old results and
temporary content, including on A→B→A. A new generation must select anew.

Call `MediaBinaryFiles.download` for a fresh authorized business-media opening;
a previously obtained file/path is not new server authorization. Dispose completed
view files when the consumer finishes. The future host supplies an app-private
temporary parent and must observe/await the file's `cleanup` failure if unlink
fails. Only owned child directories are cleanup targets. There is **no persisted
process-restart journal or cold-start orphan collector in this batch**; no such
recovery is claimed. HTTP content/header compatibility, current business read
revocation and player lifecycle remain integration acceptance gates.
